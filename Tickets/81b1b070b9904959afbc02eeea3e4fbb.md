# Public MethodIL verification seam in ILVerification and Mps.ILVerification package id

## Why

MerkleCompiler needs to ILVerify runtime-async `DynamicMethod` bodies in-process without emitting any assembly. The verification engine (`ILImporter` over abstract `MethodIL`) already has no PE dependency, but the public `Verifier` surface only accepts `PEReader`; `VerifyMethod` and `_typeSystemContext` are private. The consumer (MerkleCompiler) takes ILVerification as a package, so the seam must ship in the package. Adapter code (`DynamicMethodIL`, `DynamicMethodDesc`, runtime-to-typesystem mapper) stays out of this repository to preserve ILVerification's no-CoreLib-coupling charter.

## Change

- `Verifier.cs`: add get-only `public TypeSystemContext TypeSystemContext` and `public IEnumerable<VerificationResult> Verify(MethodIL methodIL)`. Guards: null argument; `methodIL.OwningMethod.Context` must be this verifier's context, because a `MethodIL` built against another context would be verified against foreign type-system entities; the same missing-system-module guard as the `PEReader` overloads. Delegates to `VerifyMethod` with `module: null` and `methodHandle: default`; `VerifyMethod` never reads `module`, and results carry `Method = default`. Unlike the iterator-based `PEReader` overloads, this overload validates and verifies eagerly.
- `ILVerification.csproj`: `PackageId` `Microsoft.ILVerification` -> `Mps.ILVerification` so the fork package can never collide with the nuget.org package under MerkleCompiler's source mapping. No other file in the repository references the package id.
- `internal` -> `public` promotions: none required by the seam.
- Publish `Mps.ILVerification` to `D:\feeds\LocalNuGet`.

## Environment notes

- A fresh worktree of this fork has no restore assets; `build.cmd -restore -subset clr.tools` provides them.
- That restore installs a repo-local `.dotnet` (preview 6 SDK). `global.json` lists `sdk.paths` `[".dotnet", "$host$"]`, so its presence switches every `dotnet` launched in the worktree to that SDK, whose MSBuild rejects `/reportfileaccesses` (MSB1001). The `.dotnet` directory must not remain in a transaction worktree.
- With the csproj edit, CSharpMpc takes the full `-restore /graph` build path. The CSharpMpc project-cache plugin used to fail that path in this repository (`MSBuild did not supply CacheContext.Graph for the /graph invocation`) because it was also instantiated in the `-restore` session. Fixed in CSharpMpc `e3e9748` (graph-less sessions no longer claim the handoff); after the server restart the build is a successful operation.
